# Our Space 情侣纪念空间 - 项目报告

## 一、项目概述

### 1.1 项目背景

在快节奏的现代生活中，情侣之间需要一个私密、专属的数字空间来记录和珍藏相处的点滴时光。市面上现有的社交平台（朋友圈、微博等）过于公开化，而备忘录类工具又缺乏情感化的交互体验。

**Our Space** 正是为了解决这一痛点而诞生的——一个专为情侣设计的移动端纪念空间，融合了留言互动、照片珍藏、时光记录、目标管理等功能，打造专属于两个人的数字小世界。

### 1.2 解决的痛点

| 痛点 | 解决方案 |
|------|---------|
| 社交平台公开化，不适合私密互动 | 密码保护的独立空间，仅两人可见 |
| 纪念日、重要日子容易遗忘 | 倒计时+已过天数双模式，首页轮播提醒 |
| 照片散落在各个聊天记录中 | 统一的照片墙，支持上传、浏览、管理 |
| 想说的话随时发但缺乏仪式感 | 小纸条功能，支持回复互动，留存每一句情话 |
| 共同经历缺乏时间线记录 | 故事线功能，按时间轴记录每一个重要时刻 |
| 愿望和目标没有一起规划 | 愿望清单，共同完成一起打勾 |
| 对未来的期许无处安放 | 时间胶囊，写给未来的对方，到期才能打开 |

### 1.3 产品特色

- **情侣CP感设计**：粉色（她）+ 蓝色（他）双色主题，贯穿整个产品的身份标识系统
- **移动端优先**：专为手机端设计的交互体验，底部导航、左滑切换、下拉刷新
- **双重模式**：支持本地 Demo 模式（无后端也可用）和 Supabase 云端模式
- **情感化交互**：心跳动画、轮播效果、骨架屏加载、弹出动效等细节体验

## 四、问题与解决方案

### 4.1 技术难题一：照片上传的原子性问题

**问题描述**：
照片上传涉及 Storage 文件上传 + 数据库记录写入两个操作，任何一步失败都会导致数据不一致。如果先删文件再删 DB 记录，DB 删除失败会产生"幽灵记录"；反之则会留下"孤儿文件"。

**解决方案**：
- 采用"先删数据库，后删文件"的顺序
- 数据库删除成功后再删除 Storage 文件
- Storage 删除失败只记录日志，不影响用户体验（接受最终一致性）
- 文件上传失败时，回滚数据库记录

**代码位置**：`src/hooks/usePhotos.ts`

### 4.2 技术难题二：移动端键盘遮挡输入框

**问题描述**：
移动端点击密码输入框时，输入法键盘弹出后会遮挡输入框，用户需要手动滚动页面才能看到输入内容。

**解决方案**：
- 监听 `focus` 事件，触发时调用 `scrollIntoView({ block: 'center' })`
- 使用 `visualViewport` API 监听视窗变化，动态调整页面位置
- 配合 `scroll-padding-top` 确保输入框居中显示

**代码位置**：`src/components/auth/PasswordPage.tsx`

### 4.3 技术难题三：下拉刷新体验优化

**问题描述**：
初始实现使用固定 800ms 延迟模拟刷新，无论数据加载快慢都等待固定时间，Supabase 响应快时用户会看到动画在"空转"。

**解决方案**：
- 重构全局刷新事件系统，`triggerRefresh()` 返回 Promise
- 所有页面通过 `onRefresh` 注册刷新回调
- Layout 组件使用 `Promise.all` 等待所有数据加载完成
- 刷新动画时长由实际数据加载时间驱动

**代码位置**：`src/lib/refreshEvent.ts`、`src/components/layout/Layout.tsx`

### 4.4 技术难题四：URL.createObjectURL 内存泄漏

**问题描述**：
照片预览和图片压缩时使用 `URL.createObjectURL()` 创建对象 URL，但从未调用 `URL.revokeObjectURL()` 释放内存，每上传一张照片就泄漏一块内存。

**解决方案**：
- 在 `img.onload` 回调中立即 `revokeObjectURL`
- 组件卸载时清理未释放的 URL
- 切换预览图时先释放旧的 URL

**修复位置**：
- `src/components/photos/PhotoUpload.tsx`
- `src/lib/utils.ts`（compressImage 和 generateThumbnail）

### 4.5 技术难题五：localStorage 键无限增长

**问题描述**：
时间胶囊的已读状态使用独立的 localStorage 键（`capsule_viewed_X`），每个胶囊被查看后新增一个键，数量会无限增长。

**解决方案**：
- 改用单个键 `capsule_viewed_ids` 存储所有已读 ID 的 JSON 数组
- 读写时解析/序列化数组
- 减少键数量，便于清理和管理

**代码位置**：`src/components/notes/CapsuleCard.tsx`

### 4.6 技术难题六：首页照片轮播体验

**问题描述**：
轮播方案经历多次迭代：单张大图 → 3张网格一次性切换 → 传送带式单步滑动，用户始终觉得"不够丝滑"。

**最终方案**：
- 3 张照片并排 grid 布局
- 每次移动 1 张位置（传送带效果）
- 4 秒自动切换
- 左右滑动 + 淡入淡出过渡
- 底部小圆点指示器
- Framer Motion AnimatePresence 实现平滑过渡

**代码位置**：`src/components/home/HomePage.tsx`

### 4.7 技术难题七：地图瓦片国内访问

**问题描述**：
最初使用 OpenStreetMap 瓦片，国内访问速度极慢，大量瓦片加载失败导致地图一片灰色。

**解决方案**：
- 切换至高德地图矢量瓦片（国内 CDN）
- 配置 4 个子域名轮询（webrd01-04）
- 增加瓦片加载失败计数，失败过多时降级显示
- 优化 Leaflet 配置，提升缩放和拖拽流畅度
