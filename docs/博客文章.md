# 3天用AI造了一个情侣专属的数字小世界：Our Space 开发全记录

> 当产品经理遇上 AI 全栈工程师，会碰撞出怎样的火花？本文记录了我用 3 天时间，与 AI 协作完成一个情侣纪念应用的全过程。

## 一、为什么做这个项目

恋爱中的人都懂——

朋友圈太公开，有些情话只想说给 TA 听；
聊天记录太散乱，想找一张合照要翻半天；
纪念日记不住，到了跟前才慌忙补礼物；
那些一起经历的点点滴滴，散落在各个 App 里，没有一个专属的地方安放。

我想要的，是一个只属于两个人的数字空间——私密、温暖、有仪式感。

于是，**Our Space** 诞生了。

## 二、我是怎么用 AI 开发的

先上结论：**整个项目从 0 到上线，我只花了 3 天，而如果纯手动开发，大概需要 2-3 周。效率提升 5-8 倍。**

我的角色是"产品经理 + 测试工程师 + 最终决策者"，AI 是我的"全栈开发工程师"。

### 2.1 第一天：搭架子 + 核心功能

**上午：项目初始化（10分钟 vs 传统2小时）**

我告诉 AI："给我搭一个 React + TypeScript + Vite + Tailwind CSS v4 的项目，主题色用樱花粉，目录结构要清晰。"

10分钟后，项目跑起来了。配置文件、目录结构、路径别名、主题定制，全都弄好了。换作以前，光折腾 Tailwind v4 的配置可能就要半小时。

**下午：6 个页面 + 9 个自定义 Hook**

我逐个描述每个页面的功能和交互：

- "首页要有认识天数翻牌动画、倒计时轮播、照片传送带"
- "小纸条支持回复，最新回复预览在卡片底部，点击展开"
- "时间胶囊要用信封蜡封风格，没到时间打不开"
- "照片墙上传说的照片要压缩，显示骨架屏"

每个页面，AI 大概 30-45 分钟出第一版。我提修改意见，它迭代。

最让我惊喜的是 **9 个自定义 Hook**——useNotes、usePhotos、useTimeline、useWishes... 每个都同时实现了 Demo 模式（localStorage）和 Supabase 云端模式两套逻辑，结构一致，接口统一。

### 2.2 第二天：打磨体验 + 修 Bug

第二天主要是体验优化和 Bug 修复。

我印象最深的是一次 AI 主动做的代码审查。我让它"看看代码有什么问题"，它一口气列出了 8 个问题：

1. **URL.createObjectURL 内存泄漏**（3处）——每上传一张照片就泄漏一块内存
2. **timeline_events 表 SQL 缺少 created_by 列**——真连 Supabase 会直接报错
3. **deletePhoto 原子性问题**——先删文件还是先删记录？两种失败场景都分析到了
4. **localStorage 键无限累积**——每个胶囊建一个键，越用越多
5. **generateId 碰撞风险**——同一毫秒连续调用可能重复
6. **hook 模式重复度极高**——6个hook结构几乎一模一样
7. **没有错误上报**——出错了用户不知道
8. **图片压缩没有大小限制**——传50MB原图可能撑爆内存

说实话，有几个问题我自己都没意识到。比如内存泄漏，我知道 createObjectURL 需要 revoke，但写的时候总是忘。AI 一次性帮我找出来了。

### 2.3 第三天：移动端适配 + 部署

最后一天是移动端适配和上线。

AI 基于经验提前做了很多适配：
- iPhone 底部安全区（Home Indicator）
- 灵动岛适配（Toast 位置往下挪）
- 键盘弹出时输入框自动上移
- 左滑切换页面、下拉刷新等手势交互

部署也很简单：配置 GitHub Actions，push 到 main 自动构建到 GitHub Pages。

## 三、技术选型：我为什么选这些

### 前端：React 19 + TypeScript + Vite + Tailwind CSS v4

- **React 19**：生态最成熟，Hooks 开发效率高
- **TypeScript**：类型安全，减少运行时错误，AI 生成的代码有类型更靠谱
- **Vite**：启动快，HMR 毫秒级，改完立即看到效果
- **Tailwind CSS v4**：不用写自定义 CSS，开发速度起飞，v4 比 v3 更轻量

### 动画：Framer Motion

React 生态最强大的动画库，声明式的写法跟 React 心智模型一致。AI 用起来也顺手，各种复杂动画几行代码搞定。

### 后端：Supabase

Firebase 的开源替代，PostgreSQL + Storage + 实时订阅，开箱即用。对于两个人的小应用，免费额度完全够用。

### 部署：GitHub Pages + GitHub Actions

免费、稳定、自动化。push 代码就自动部署，不用管服务器。

## 四、几个印象深刻的技术难题

### 难题一：照片上传的原子性问题

照片上传涉及两个操作：Storage 存文件 + 数据库写记录。

问题来了：先做哪个？
- 先存文件，写库失败 → 文件变成"孤儿"
- 先写库，存文件失败 → 数据库有"幽灵记录"

我们的方案：**接受最终一致性**。删除时先删数据库，再删文件；文件删失败了就记日志，不影响用户体验。上传时先存文件，再写库；写库失败了回滚删文件。

不是完美的方案，但对于两人用的小应用，权衡下来是最合适的。

### 难题二：首页照片轮播的"丝滑感"

轮播这个功能，我们迭代了三版：

1. **单张大图轮播**——太单调
2. **3张网格，一次性切换**——太跳，不连贯
3. **传送带式，每次移1张**——终于对味了

最终方案：3张并排 grid 布局，4秒自动切换，每次移动一张位置，配合淡入淡出过渡，底部小圆点指示器。用 Framer Motion 的 AnimatePresence 实现平滑过渡。

就这么一个小功能，前前后后调了好几版。AI 的好处是——改起来快，我说"改成传送带效果"，它几分钟就出代码，我可以快速试错找到感觉。

### 难题三：地图瓦片国内访问（后来移除了）

中间做过一个"共享位置"功能，最初用 OpenStreetMap 瓦片，国内访问巨慢，地图一片灰。

后来切换到高德地图矢量瓦片，配置4个子域名轮询，加载速度快了很多。但最终因为各种原因（定位权限、https 要求、用户实际需求不强），还是把这个功能移除了。

虽然功能没留下，但这次预研让我对 Leaflet 和国内地图瓦片有了了解，也算收获。

## 六、AI 协作的心得

做这个项目的过程中，我对"如何与 AI 高效协作"有了一些体会：

### 1. 需求要具体，别让 AI 猜

"做一个好看的首页" → AI 会给你一个平庸的结果
"首页顶部放认识天数翻牌动画，下面是倒计时卡片轮播，再下面是3张照片传送带，4秒自动切换" → 结果会好很多

### 2. 大功能拆小步，每步验证

别指望 AI 一次性给你一个完美的大功能。拆成小步骤，每步确认后再往下走，反而更快。

### 3. 给足上下文

项目架构、代码风格、已有的组件和工具函数……告诉 AI 越多，它生成的代码越贴合你的项目，返工越少。

### 4. 主动审查，别盲目相信

AI 会犯错。业务逻辑、边界条件、性能问题，还是要人来把关。但 AI 的好处是——它写第一版很快，人只需要 review 和修改，比从零开始写省很多时间。

### 5. 积累记忆

好的 AI 协作是"越用越顺手"的。项目记忆、代码约定、设计风格……这些东西积累下来，后面的对话效率会越来越高。

## 七、写在最后

这个项目是我第一次完整地用"人类产品经理 + AI 开发者"的模式做一个完整应用。

最大的感受是：**AI 不是来取代人的，而是把人从重复劳动中解放出来，让人能更专注于产品本身。**

以前做项目，大量时间花在"写"代码上——写 HTML、写 CSS、写 CRUD、写样板代码。现在这些 AI 都帮你做了，人可以把精力放在更重要的事情上：想清楚要什么、体验好不好、逻辑对不对。

3 天时间，从想法到上线，放在以前我想都不敢想。

这是最好的时代——每个人都可以成为创造者。
